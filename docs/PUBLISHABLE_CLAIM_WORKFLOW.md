# Workflow: Production Data → Publishable Claim

**Closes Verification Master Checklist Cat 4 item:** "Workflow documented from production data → defensible publishable claim."

This document specifies the procedure VoxCore uses to take a measurement from "we just ran something" to "this is a number we will defend in front of an acquirer engineer or in technical diligence." It is the operational expression of the methodology rules in `~/.claude/projects/C--Users-atayl-VoxCore/memory/feedback_calibration_overfit.md`.

The workflow is a **gate**: a measurement that fails any of the seven steps below cannot be cited externally. Period.

---

## Step 1 — Test set must be HELD OUT from pipeline development

**Rule:** the queries used to measure cannot be the queries used to design or tune the prompt, scorer, or retriever.

**Operational test:** point at the queries file. If it appears anywhere in (a) a calibration loop, (b) a prompt template, (c) any tooling that influenced the measured pipeline's behavior, the test set is contaminated.

**Evidence requirement:** every published number must cite the queries-file path AND a one-line provenance note (e.g. "generated by Claude Opus 2026-05-02 from case-status / case-contacts / case-filings memory with explicit calibration-batch exclusions").

**Failure example:** the 2026-05-02 calibration n=15 batch hit 0.0% hallucination on the same pipeline that scored 30.0% on a fresh held-out n=35. The 0% would have been a fraud claim externally; the 30% is the production-relevant number.

## Step 2 — Judge model must be specified

**Rule:** every published quality number includes the judge model used. Same answers can score 15+ percentage points differently across judges.

**Operational test:** the published claim must specify (a) the judge model id, (b) whether substring/programmatic verification is also in the path. "Hallucination rate 24.7%" without a judge name is unfit for diligence.

**Evidence requirement:** the score JSON file recorded the judge model in its top-level metadata.

**Failure example:** "Round 3 published 45.45% hallucination" was Gemma 4 26B over-flagging IRRELEVANT vs PARTIAL. Same answers, Claude Opus 4.7 judge → 30.3%. The 15pp shift was judge calibration, not pipeline change.

## Step 3 — Comparison must be apples-to-apples

**Rule:** any "X improved Y to Z" claim must use the same judge, same test set, and same scoring methodology as the baseline.

**Operational test:** baseline score JSON and improved score JSON both have identical `judge`, `judge_model`, and were run against identical input batches.

**Evidence requirement:** include both score-file paths in the citation. Document the diff in methodology if any (and explain why).

**Failure example:** comparing "Step-1 v3 (Claude judge) 0.0% calibration" vs "baseline (Gemma judge) 45.45%" — different judges, different test sets. Two unrelated numbers, not a 45pp improvement.

## Step 4 — Predictions must reference measured baselines

**Rule:** when projecting "Tier 2 will reduce hallucination from X% to Y%", X must be a measured number, not an inferred one.

**Operational test:** the X cited in the prediction can be traced to a specific score JSON (with judge labeled, held-out test set verified per Steps 1-2).

**Failure example:** the original roadmap predicted "step 1 prompt change → ~10% hallucination" using the inflated 45% Gemma baseline. After Claude judge correction the real baseline was 30%, and step 1's true held-out effect was ~0pp. The prediction was scoped against an inflated baseline → it under-stated the work remaining.

## Step 5 — Confidence-tier the claim

**Rule:** every external claim is tagged with one of: PROVEN / WELL-SUPPORTED / PARTIALLY-SUPPORTED / UNCERTAIN / WITHDRAWN.

- **PROVEN:** held-out n≥50, two independent judges agree, deterministic verification (e.g. substring) corroborates.
- **WELL-SUPPORTED:** held-out n≥30 with a single Claude-Opus-grade judge.
- **PARTIALLY-SUPPORTED:** held-out n<30 OR sample n is small AND judge calibration not validated.
- **UNCERTAIN:** measured but with documented methodology gaps (e.g. small sample, single judge known to be lenient/strict).
- **WITHDRAWN:** previously-claimed number that does not survive Steps 1-4.

## Step 6 — Pre-publication audit

**Rule:** before any number leaves the workstation in an external document (PDF, email, slide, web page), it goes through this audit.

**Audit checklist:**
- [ ] Test set is held-out per Step 1
- [ ] Judge model is named per Step 2
- [ ] Comparisons are apples-to-apples per Step 3
- [ ] Predictions reference measured baselines per Step 4
- [ ] Confidence tier is assigned per Step 5
- [ ] Score JSON path is cited (so a reviewer can verify the number themselves)
- [ ] Methodology caveats are surfaced, not buried
- [ ] If the number replaces an inferred number, the inferred number is explicitly withdrawn

**Failure mode this prevents:** a single "<2%" number in a PDF that the engineering team can't reconstruct — the diligence-killing pattern. Every external number must be a number the operator can defend in five minutes from the score JSON + a one-line methodology summary.

## Step 7 — Re-measure on each pipeline change

**Rule:** any prompt, scorer, retriever, or chunker change invalidates prior measurements until re-measured. The measured number stays valid only as long as the pipeline that produced it is unchanged.

**Operational test:** the score JSON's input filename, code commit SHA (or file mtime in lieu), and judge model are stable across the period the number is being cited. If any has changed since the measurement, re-run before citing.

**Failure mode this prevents:** today's parser fix improved calibration to 0.0% but the held-out batch was still scored under the old assumption that the calibration number generalized. Re-measuring on held-out caught the divergence; not re-measuring would have shipped the inflated calibration number externally.

---

## Cadence

- **Per pipeline change:** re-run the held-out batch + Claude judge (~$5, ~10 min). Update `Desktop/VoxCore_Benchmark_Results.md` with the new row.
- **Per session:** re-read this workflow before any external-publication work. Cite the score JSON, not the conversation summary.
- **Weekly (post-launch):** spot-check 5 random claims in any external document against their score JSONs. Withdraw any that fail Steps 1-5.
- **Pre-acquirer-call:** full re-audit per Step 6, with the auditor explicitly checking each cited number against its score JSON.

## Roles

- **Operator (Adam):** owns the WITHDRAWN dispositions and any external-publication go/no-go.
- **Claude Code:** runs the pipeline, captures the score JSONs, drafts the audit checklist, refuses to publish any number that fails Steps 1-5.
- **Triad Auditor (Gemini):** can be asked to re-validate a published claim against its evidence — independent third-party check.
